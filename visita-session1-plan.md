## 2. Schema

### Helpers (migration 100)
- The `citext` extension.
- A `set_updated_at()` trigger function.
- **`user_roles`** (`user_id` → auth.users, `role` enum `app_role` = `'admin'`). Nobody can write to it through the API; it's granted via SQL or the service role only. `role` doesn't go on `profiles` because users can update their own profile, which is how privilege-escalation bugs happen.
- **`is_admin()`**, a `security definer`, `stable` function. Policies call it as `(select is_admin())` so it runs once per query, not once per row.

### `profiles`
- Columns: `id` (PK → auth.users), `display_name`, `avatar_url`, timestamps.
- A trigger on `auth.users` insert creates the row automatically from the Google metadata.
- It only holds what's safe to show publicly, since review authors' names are public. Anything private goes in another table.

### `venues`

| column | type | notes |
|---|---|---|
| id | uuid PK | |
| slug | citext unique | for deep links (see decision B) |
| venue_type | enum `venue_type` | `cafe`, `pickleball_court`, `function_room`, `airbnb` |
| name, address | text | |
| city | text | default `'Cagayan de Oro'` |
| lat, lng | double precision | for pins, distance and check-in geofencing. No PostGIS yet. |
| google_place_id | text unique, nullable | links unscanned cafes and the Places fallback |
| splat_url | text, nullable | R2 object path. Null means unscanned (white pin). |
| scanned_at | timestamptz, nullable | the scan date shown on the page |
| amenities | jsonb not null default `'{}'` | check: must be an object. Unknown fields are left out rather than stored as null, which matches "unknown fields don't render". |
| hours | jsonb, nullable | structured hours; the TS type lives in shared-types |
| is_top_pick | bool default false | |
| is_published | bool default false | drafts stay invisible to the public |
| created_at, updated_at | timestamptz | |

### `reviews`
- Columns: `id`, `venue_id`, `author_id` (default `auth.uid()`), `rating` smallint 1–5, `body`, `photo_url` (nullable), `status` enum `visible` / `hidden` (for moderation), timestamps.
- **unique (venue_id, author_id)**: one review per person per venue, which closes the easiest way to farm points.

### `review_awards`
- `id`, `review_id`, `giver_id`, `points` > 0, `created_at`.
- A check blocks self-awards. This is a judgment call; see decision D.

### `point_events` (an append-only ledger, and the only source of truth for balances)
- Columns: `id` bigserial, `user_id`, `amount` int (negative for spending on awards), `reason` enum, `source_id` uuid (nullable), `created_at`.
- `reason` values: `review`, `review_photo`, `first_review`, `amenity_confirm`, `outdated_report`, `check_in`, `streak`, `referral`, `referral_milestone`, `award_given`, `award_received`, `admin_adjustment`.
- **A partial unique index on (user_id, reason, source_id)** makes awarding idempotent: a retried Worker call can't pay out twice.
- A `point_balances` view with `security_invoker` shows your own balance.
- The public leaderboard comes later as a `security definer` function that returns only aggregates.

### `badges` (the catalog) and `user_badges`
- `badges`: `id` text slug PK, `name`, `description`, `category`, `threshold` (nullable). The table starts empty, because badge names are a product decision.
- `user_badges`: PK (`user_id`, `badge_id`), `awarded_at`.

### `check_ins`
- Columns: `id`, `user_id`, `venue_id`, `status` enum `pending` / `verified` / `rejected`, `started_at`, `verified_at`, `start_distance_m`, `end_distance_m`, `accuracy_m`, `rejection_reason`.
- It stores **distance from the venue, not raw GPS coordinates** (decision C).

### `referral_codes` and `referrals`
- `referral_codes`: `user_id` PK, `code` citext unique. It's separate from `profiles` so codes aren't publicly listable.
- `referrals`: `id`, `referrer_id`, `referred_id` (**unique**, so a user can only be referred once), `status` enum `pending` / `qualified` / `rejected`, `qualified_at`, `created_at`. A check blocks self-referral.

### Not built yet
Amenity verifications, outdated-info reports, vouchers, menus, venue owners, the demand queue, analytics and the audit log.

## 3. Row-Level Security

RLS is on for every table.

| Table | Public (anon) read | Authenticated user | Admin |
|---|---|---|---|
| venues | only `is_published = true` | read published | full CRUD |
| reviews | only `status = 'visible'` | insert as themselves; can update only `rating`, `body` and `photo_url` on their own review (column-level grant, so they can't un-hide it); delete their own | full, including `status` |
| review_awards | read | read (inserts come later through an RPC that checks and debits points) | full |
| profiles | read | update own `display_name` and `avatar_url` | full |
| point_events | none | read own | read all |
| badges / user_badges | read | read | full |
| check_ins | none | read own | read all |
| referral_codes / referrals | none | read own (as referrer or referred) | read all |
| user_roles | none | none | read |

**The main rule: users never insert into `point_events`, `user_badges`, `check_ins` or `referrals` directly.** Those writes happen only in the Cloudflare Workers (using the service role), matching PRD 5.5. Letting clients write them would make farming points trivial.

On venues, "owner" means admin for now. Venue-owner edit rights come with the listing editor, because owner changes to amenities have to go through the approval queue anyway.

## 5. Decisions to review (veto any of these)

**A. The PRD's prerendered venue page has a freshness problem.** If `/venue/[slug]` is built at deploy time, a new venue or rescan needs a rebuild, and a newly written review won't appear until the next deploy. Recommendation:
- keep the venue page prerendered;
- trigger a Cloudflare deploy hook when a venue is published or rescanned;
- render reviews and the personalized parts (saved heart, check-in state, "your review") as Astro server islands (`server:defer`), so the static shell stays cached and those parts load fresh per request.

`/community` has the same problem with "recent activity", and the same fix works there. The skeleton will include those server-island placeholders.

**B. `/venue/[slug]` instead of the PRD's `[id]`.** It gives readable share links. The UUID stays the internal key.

**C. Check-ins store distance, not raw coordinates.** That means less personal data under RA 10173. Spoofing checks (implausible travel speed between check-ins) can still use the venue coordinates. If raw coordinates are wanted for fraud forensics, they can be added with a retention note.

**D. `review_awards` is the one table outside the requested list.** It's included because awards are the only way points get spent, and that shapes the ledger design. Cutting it is easy.

**E. Unscanned cafes are `venues` rows** with a null `splat_url`, so white pins and, later, the demand button have something to point at.

## 7. Revisions after the prototype review (2026-09-24)

The client prototype was used for **flow, content and inspiration only**, not architecture.

**Decisions**
- **A.** Walkthroughs are PlayCanvas `.sog` only. The prototype's Luma captures are legacy and will be re-exported.
- **B.** Amenities are fully configurable: an `amenity_definitions` table (per venue type: label, icon, value type, unit, filterable, summary-strip rank, sort order, needs-verification, active). Each stored amenity is `{label?, value?}`, validated by a trigger.
- **C.** `venues.menu` is jsonb for now (`[{name, price_php?, section?, note?}]`), validated. It moves to its own table with the owner menu editor.
- **D.** The prototype's `cafes.json` is imported for local testing via `pnpm db:import-prototype`.

**Schema changes**
- `venues` gains `search_terms text[]` and `menu jsonb`.
- `hours` uses `{mon: ["08:00","20:00"] | null, ...}` (missing = unknown, null = closed).
- The scan constraint is relaxed to "a scan date requires a scan". A scan with no known date is allowed, and the UI shows no date.

**Route changes**
- `/venue/[slug]` becomes `/cafe/[slug]`. `/map` is replaced by `/` (map hero + marketing) and `/explore` (map only).
- Added `/for-cafes`, `/about`, `/contact` and `/faq`.
- The walkthrough is an overlay in the map island that pushes `/cafe/<slug>`.
- The domain is `visita.ph`.
